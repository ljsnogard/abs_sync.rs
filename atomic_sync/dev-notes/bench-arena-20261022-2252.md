# cooperative 读写锁：Arena 队列与堆分配队列的基准计划

## 1. 目的

`cooperative-arena` feature 已经提供了一套对外 API 完全一致的 Arena +
侵入式链表等待队列实现。本文记录第一轮冒烟基准，并给出后续用于判断"哪一版
在什么场景下更好"的测试计划。

当前结论只用于**发现信号**，不作为选型依据。

## 2. 冒烟基准条件

- 日期：2026-10-22
- 工具链：`rustc 1.101.0-nightly (4ebd25825 2026-10-15)`
- 机器：当前开发机，进程 4 线程；未做 CPU 绑核与频率固定
- 每个竞争者 5000 次操作，每项取 3 轮最好成绩，临界区自旋 8
- 负载：
  - `readheavy`：读 75% / 写 15% / 升级 5% / 让出 5%
  - `writeheavy`：读 40% / 写 40% / 升级 15% / 让出 5%
- 命令：

```sh
RWLOCK_BENCH_OPS=5000 RWLOCK_BENCH_ROUNDS=3 \
RWLOCK_BENCH_COMPETITORS=1,2,4,8 \
cargo bench -p atomic_sync --bench rwlock_cooperative

RWLOCK_BENCH_OPS=5000 RWLOCK_BENCH_ROUNDS=3 \
RWLOCK_BENCH_COMPETITORS=1,2,4,8 \
cargo bench -p atomic_sync --features cooperative-arena \
  --bench rwlock_cooperative
```

原始输出保存在工作区 `.tmp/bench_default_baseline.txt` 与
`.tmp/bench_arena_baseline.txt`（不随仓库提交）。

## 3. 冒烟结果

表中是 cooperative 的 ns/op；括号内是 Arena 相对默认值的增减（负数表示
Arena 更快）。

### readheavy

| 运行时 | N=1 | N=2 | N=4 | N=8 |
|---|---:|---:|---:|---:|
| tokio 多线程 | 83.5 → 89.3 (+6.9%) | 136.8 → 132.3 (-3.3%) | 82.9 → 89.9 (+8.4%) | 528.3 → 504.4 (-4.5%) |
| compio 单线程 | 85.4 → 82.5 (-3.4%) | 56.8 → 53.9 (-5.1%) | 58.4 → 52.5 (-10.1%) | 58.0 → 53.6 (-7.6%) |
| OS 线程 | 77.3 → 75.1 (-2.8%) | 80.0 → 79.9 (-0.1%) | 3357.7 → 3278.1 (-2.4%) | 14400.4 → 11766.6 (-18.3%) |

### writeheavy

| 运行时 | N=1 | N=2 | N=4 | N=8 |
|---|---:|---:|---:|---:|
| tokio 多线程 | 79.6 → 82.2 (+3.3%) | ⚠ 292.2 → 81.8 | 188.3 → 194.2 (+3.1%) | 940.4 → 767.7 (-18.4%) |
| compio 单线程 | 93.0 → 89.9 (-3.3%) | 63.2 → 61.0 (-3.5%) | 65.8 → 59.7 (-9.3%) | 65.5 → 59.5 (-9.2%) |

### 噪声与异常

- OS 线程一节 cooperative 使用 `block_on` 驱动，和另两个实现的线程模型不同；
  N=4/8 的绝对延迟在微秒级，调度噪声远大于队列实现差异，不能单独用来选型。
- 两个 ⚠ 单元格在复测中方向不稳定：
  - writeheavy / tokio / N=2，放大到 20000 ops × 5 轮：默认 303.7 ns，
    Arena 254.6 ns（Arena -16.2%）。
  - writeheavy / OS 线程 / N=2，同样放大：默认 6810.5 ns，Arena 81.1 ns；
    但 5000 ops 时又出现相反方向。该组合受 `block_on` 调度影响，后续应从
    队列结论中剔除，或单独用固定线程模型和 CPU 绑核分析。
- tokio N=8 的整轮总耗时达到几十毫秒，说明已经出现明显的调度/唤醒放大；
  单轮 ns/op 的方差很大。

### 唯一较稳定的信号

compio 单线程执行器没有真实线程并行，调度噪声最小。两种负载下 Arena 都稳定
快 3%～10%，且竞争者越多优势越明显。这与"Arena 省掉每节点 `Arc` 分配与
引用计数"的预期一致，但幅度仍需要更多轮次确认。

## 4. 差异来源与预测

| 优先级 | 差异点 | 预期方向 | 如何暴露 |
|---|---|---|---|
| P0 | 每个等待节点一次 `Arc` 分配 vs Arena 槽位复用 | 高churn/多线程下 Arena 明显更快 | 统计分配次数；持续 acquire/release 压测 |
| P0 | 深队列：`VecDeque` 扩容/搬移 vs 固定 1024 槽 chunk | 队列深度跨过 1024 时 Arena 更稳 | 队列深度扫描 1→4096 |
| P0 | 锁内全局分配 vs 锁内空闲链索引 | 高竞争下 Arena 临界区更短 | 多线程高争用 + `sched` 延迟/临界区计时 |
| P0 | 取消风暴：`Arc` 析构 vs 槽位归还 | Arena 更快、分配器压力更小 | 入队后按比例取消 |
| P1 | 首次竞争：Arena 一次初始化 1024 个槽 | 首次竞争 Arena 更慢、内存跳变更大 | 冷启动首次入队时延 |
| P1 | 空 chunk 立即归还 vs 保留一个空 tail chunk | Arena 稳态内存更高、下次突发更快 | RSS/分配峰值、突发-排空-再突发 |
| P2 | 读类节点合并：`Arc::clone` vs 裸指针 | Arena 小胜 | 写者阻塞下的批量读者 |
| P2 | 升级插队：`VecDeque::push_front` vs 链表 | 差异小，Arena 略优 | 升级密集负载 |
| 对照 | 快速路径（无队列） | 应接近 0 | 单线程 try_read/try_write |

## 5. 测试计划

### 阶段 0：正确性与可重复性（已有）

- 两套实现共用同一份行为测试；默认与 `--features cooperative-arena` 分别跑
  全量测试。
- Arena 池与 `RwCoreArena` 队列已有 Miri（strict provenance）覆盖。
- 基准前置条件：固定 CPU 核、记录 cpufreq、同一二进制构建参数、同一随机种子。

### 阶段 1：隔离队列行为（新增场景）

1. **fastpath**：单线程无竞争 `try_read`/`try_write` 循环。
   - 预期：两版差异 ≤3%。
   - 作用：排除核心大小/间接层导致的基础开销差异。
2. **cold-first-contention**：反复创建新锁，先取写者，再让 1 个等待者入队并释放。
   - 指标：首次入队时延、首次 chunk 分配次数、RSS 增量。
   - 预期：Arena 因 1024 槽初始化与整块分配而更慢。
3. **queue-depth sweep**：写者持有，分别排队
   `1,2,4,...,512,1024,2048,4096` 个读者/写者，再释放并 drain。
   - 指标：入队/唤醒/回收总时延、每等待者 ns、队列峰值、chunk 数/分配次数。
   - 预期：深度 >1024 后 Arena 优势扩大；原版在 VecDeque 扩容点出现阶跃。
4. **cancel-storm**：入队 K 个等待者后取消 0/25/50/75/100%，再释放写者。
   - 指标：取消时延、drain 时延、分配/释放次数、队列残留。
   - 预期：Arena 明显更少分配器调用。
5. **reader-coalesce**：写者阻塞，连续入队大量读类等待者。
   - 指标：每个读者入队成本、节点数（Arena 合并后槽位数）、唤醒批大小。
   - 预期：Arena 仅省掉尾节点 `Arc::clone`，差异小。
6. **upgrade-head**：可升级读者与写者交替，检验插队路径。
   - 指标：升级等待时延、`WRITER_QUEUED` 保持时间。
   - 预期：差异小。
7. **memory-burst**：一次深队列峰值后排空，记录 RSS/分配峰值与稳态。
   - 预期：Arena 稳态保留一个空 tail chunk，内存高于原版；下次突发更快。

### 阶段 2：混合负载统计

- 负载集合：readheavy / writeheavy / readonly / noupgrade。
- 竞争者：1/2/4/8/16；分别跑 tokio 多线程、compio 单线程、OS 线程。
- 每项至少 10 轮，报告 median、p95、p99、max；不要只取最好轮。
- 交替运行两版二进制，避免温度/频率漂移只影响其中一版。

### 阶段 3：判定

建议的初步阈值（待阶段 1 数据校准）：

- 快速路径回退不超过 3%；
- 深队列/取消风暴/持续 churn 的吞吐提升至少 10%，或 p99 改善至少 15%；
- 内存：Arena 稳态增量可解释（一个 chunk）且可接受；
- 若收益只出现在 compio 单线程且幅度 <5%，则保留 feature 为实验性，不默认开启。

## 6. 需要补充的基准设施

- 新 bench 场景/环境变量：`RWLOCK_BENCH_SCENARIO=fastpath|queue_depth|cancel|coalesce|upgrade|memory`，
  以及 `RWLOCK_BENCH_WAITERS`、`RWLOCK_BENCH_CANCEL_PCT`。
- 全局分配器计数包装：统计分配/释放次数、字节数、峰值；用于直接验证
  "每节点 Arc vs 每 chunk 一次分配"。
- 延迟直方图（p50/p99/p999/max），而不是只统计整轮吞吐。
- RSS/`VmHWM` 采样；可选 `smaps_rollup`。
- CPU 绑核与固定频率说明；每轮开始前 warmup，结束后冷却。
