# cooperative 读写锁：Arena 队列与堆分配队列的基准计划

## 1. 目标与边界

Arena 版的设计目标：

1. 等待路径上除了申请 chunk，不再发生任何运行时堆分配；
2. 队列锁只保护拓扑，不覆盖唤醒；
3. 已放行的读者直接领取，不需要为了领取再取队首锁。

当前实现（`cooperative_arena/`）：

- 等待节点与等待槽位都是 `ArenaItem`，来自同一个 `Arena<ArenaItem>`；
- 节点间是侵入式双向链表，节点内槽位是侵入式单链，没有 `Vec`；
- 被选中的读节点会 `sealed_`，新读者不再合并进来；
- `waking_` 保证同一节点只有一个唤醒者，并阻止唤醒期间节点被回收；
- 唤醒者在锁外逐个槽位取 waker 并 `wake`，不收集批、不按固定容量重取锁；
- `Admitted` 槽位直接 CAS 领取；只有最后一个 pending 槽位的完成者取一次
  队列锁推进队列（`finalizing_` 认领收尾）；
- 唤醒者发现队首正在被处理时，通过 `retry_` 让当前唤醒者清标记后重跑，避免
  并发设置 waker 时丢唤醒。

不在本目标内、仍会发生的分配：

- `CooperativeRwLock::new` 里的 `Arc<RwCoreArena>`（锁构造，不是等待路径）；
- 运行时对 `Waker::clone` / `wake` 的内部处理（不属于本 crate 的堆使用）；
- 测试代码里的 `Vec`。

## 3. 冒烟结果

只列 compio 单线程一节：它没有真实线程并行，调度噪声最小，最适合观察队列
实现差异。tokio / OS 线程的结果见原始日志，当前受调度噪声主导。

| 负载 | N=1 | N=2 | N=4 | N=8 |
|---|---:|---:|---:|---:|
| readheavy 默认 | 86.8 ns | 60.5 ns | 59.5 ns | 58.6 ns |
| readheavy Arena | 81.1 ns | 52.6 ns | 53.9 ns | 53.3 ns |
| writeheavy 默认 | 93.4 ns | 67.0 ns | 64.9 ns | 65.0 ns |
| writeheavy Arena | 87.6 ns | 59.0 ns | 58.3 ns | 60.9 ns |

相对默认实现，Arena 版在 compio 下快 **6%～13%**。

### 与上一版（队列锁内收集/分批唤醒）的对比

上一版在 compio 下：
readheavy 约 84.8 / 58.6 / 56.9 / 59.3 ns，writeheavy 约 91.6 / 65.0 /
64.4 / 64.2 ns。

改成"队列锁只保护拓扑 + 锁外逐个唤醒 + 读者无锁领取"后，compio 下再快
约 **5%～10%**。说明锁粒度和分批唤醒确实是主要问题，而不是单纯的 Arena
分配成本。

### 噪声与异常

- OS 线程一节 cooperative 使用 `block_on` 驱动，N≥2 的绝对延迟仍在微秒级，
  调度噪声远大于队列实现差异；这一节只作参考。
- tokio 多线程在 N=8 附近多次出现几十毫秒的整轮耗时，单轮 ns/op 的方差很大。
- 期间修复了两个并发问题：
  - 跨批升级放行：不能把已 `Acquired` 的旧可升级读槽位当成仍占用名额；
  - 节点提前回收：最后一个 pending 槽位完成时用 `finalizing_` 认领收尾，
    避免槽位完成线程还在访问节点时被其他线程 prune 掉（曾表现为
    `ArenaItem: 期望 Node，实际是 Slot`）。

## 4. 差异来源与预测

| 优先级 | 差异点 | 预期方向 | 如何暴露 |
|---|---|---|---|
| P0 | 节点 `Arc` + `Vec` 分配 vs Arena 元素 | 高 churn/多线程下 Arena 更少分配 | 分配计数；持续 acquire/release |
| P0 | 队列锁内的唤醒收集/分批 vs 锁外逐个唤醒 | 读者批越大 Arena 越占优 | 读者数 1→4096，比较唤醒段耗时 |
| P0 | 读者领取是否取队列锁 | 高并发读者下 Arena 扩展性更好 | 多读者同时 poll 的吞吐 |
| P0 | 节点 `sealed_` 后新读者走快路径/新节点 | 新读者不应拖慢正在唤醒的节点 | 唤醒期间持续注入读者 |
| P0 | 最后完成者推进队列 | 不应出现无人唤醒下一个 | 大读者批释放后写者延迟 |
| P1 | 深队列：`VecDeque` 扩容 vs 固定 1024 chunk | 跨 1024 时 Arena 更稳 | 队列深度扫描 |
| P1 | 首次竞争：Arena 一次初始化 1024 元素 | 首次竞争 Arena 更慢、RSS 跳变更大 | 冷启动首次入队时延 |
| P1 | 空 chunk 立即归还 vs 保留空 tail chunk | Arena 稳态内存更高、下次突发更快 | RSS/分配峰值，突发-排空-再突发 |
| P2 | 读类节点合并：`Arc::clone` + Vec push vs 链表追加 | 小节点差异小，大节点待测 | 写者阻塞下批量读者 |
| P2 | 升级插队：`VecDeque::push_front` vs 链表 | 差异小 | 升级密集负载 |
| 对照 | 快速路径（无队列） | 应接近 0 | 单线程 try_read/try_write |

## 5. 测试计划

### 阶段 0：正确性与可重复性（已有）

- 两套实现共用同一份行为测试；`cargo test` 会同时运行两者。
- Arena 池与 `RwCoreArena` 队列已有 Miri（strict provenance）覆盖。
- 基准前置条件：固定 CPU 核、记录 cpufreq、同一二进制构建参数、同一随机种子。

### 阶段 1：隔离队列行为（新增场景）

1. **fastpath**：单线程无竞争 `try_read`/`try_write` 循环。
   - 预期：两版差异 ≤3%。
2. **cold-first-contention**：反复创建新锁，先取写者，再让 1 个等待者入队并释放。
   - 指标：首次入队时延、chunk 分配次数、RSS 增量。
   - 预期：Arena 因 1024 元素初始化与整块分配而更慢。
3. **queue-depth sweep**：写者持有，分别排队
   `1,2,4,...,512,1024,2048,4096` 个读者/写者，再释放并 drain。
   - 指标：入队/唤醒/回收总时延、每等待者 ns、chunk 数/分配次数。
   - 预期：深度 >1024 后 Arena 优势扩大；原版在 VecDeque 扩容点出现阶跃。
4. **new-reader-during-wake**：唤醒一个大读者批期间持续注入新读者。
   - 指标：新读者快路径成功率、是否创建新节点、唤醒线程被拖慢多少。
   - 预期：`sealed_` 阻止合并；新读者不改变正在唤醒的节点。
5. **cancel-storm**：入队 K 个等待者后取消 0/25/50/75/100%，再释放写者。
   - 指标：取消时延、drain 时延、分配/释放次数、队列残留。
6. **reader-coalesce**：写者阻塞，连续入队大量读类等待者。
   - 指标：每个读者入队成本、节点数/槽位数、唤醒段耗时。
7. **upgrade-head**：可升级读者与写者交替，包含多个可升级读请求共用节点。
   - 指标：升级等待时延、`WRITER_QUEUED` 保持时间、跨批误判。
8. **memory-burst**：一次深队列峰值后排空，记录 RSS/分配峰值与稳态。
   - 预期：Arena 稳态保留一个空 tail chunk，内存高于原版；下次突发更快。

### 阶段 2：混合负载统计

- 负载集合：readheavy / writeheavy / readonly / noupgrade。
- 竞争者：1/2/4/8/16；分别跑 tokio 多线程、compio 单线程、OS 线程。
- 每项至少 10 轮，报告 median、p95、p99、max；不要只取最好轮。
- 交替运行两版二进制，避免温度/频率漂移只影响其中一版。

### 阶段 3：零分配验证

- 在专用 bench/test 二进制里安装计数型全局分配器。
- 预热到 chunk 已分配、队列进入稳态后清零计数；
- 执行 K 次"入队 → 唤醒 → 领取 → 释放"，断言**除 chunk 分配外**分配计数
  为 0；按分配大小分类，明确只允许 chunk 尺寸。
- 单独验证：
  - 读类大节点合并（槽位链增长）；
  - 取消风暴（槽位不单独释放，节点整体回收）；
  - 锁外逐个唤醒路径；
  - `sealed_` 节点与新读者。
- 同时记录 `Waker::clone` 是否触发了运行时分配，区分"本 crate 分配"与
  "运行时分配"。

### 阶段 4：判定

建议的初步阈值（待阶段 1/3 数据校准）：

- 快速路径回退不超过 3%；
- 深队列/取消风暴/持续 churn 的吞吐提升至少 10%，或 p99 改善至少 15%；
- 无分配目标必须满足（稳态 0 次本 crate 堆分配）；
- 内存：Arena 稳态增量可解释（一个 chunk）且可接受；
- 若收益只出现在 compio 单线程且幅度 <5%，则保留 feature 为实验性，不默认开启。

## 6. 需要补充的基准设施

- 新 bench 场景/环境变量：`RWLOCK_BENCH_SCENARIO=fastpath|queue_depth|cancel|coalesce|upgrade|memory`，
  以及 `RWLOCK_BENCH_WAITERS`、`RWLOCK_BENCH_CANCEL_PCT`。
- 全局分配器计数包装：统计分配/释放次数、字节数、峰值；用于直接验证
  "每节点 Arc/Vec vs 每 chunk 一次分配"。
- 延迟直方图（p50/p99/p999/max），而不是只统计整轮吞吐。
- RSS/`VmHWM` 采样；可选 `smaps_rollup`。
- 按槽位统计队列锁/节点锁的获取次数，验证"读者领取不再取队列锁"。
